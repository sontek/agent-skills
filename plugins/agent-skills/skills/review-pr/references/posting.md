# Posting comments

Only reached **after** the user has approved specific comments (step 6). If they said "none" or only wanted the text, stop — don't post.

## Requires

GitHub CLI (`gh`) authenticated, and an open PR for the branch. If the branch has no PR, offer to open one with `create-pr` first, or just hand back the comments as text.

## Identify the PR

```bash
gh pr view --json number,url,headRefName
```

## Line-anchored review comments (preferred)

Inline comments attach to a file + line in the PR diff. Post them as a single review so the author gets one notification, not N:

```bash
gh api repos/{owner}/{repo}/pulls/{number}/reviews \
  -f event=COMMENT \
  -f body="<optional overall summary>" \
  -f 'comments[][path]=src/orders/api.py' \
  -F 'comments[][line]=42' \
  -f 'comments[][body]=**blocking** — `lookup_customer` returns None on a miss, so `customer.email` will throw here. Guard it or return early?'
```

Repeat the `comments[][...]` triplet (path, line, body) for each approved comment in the same call. `line` is the line number in the file's new version; for a comment on the old side use `side=LEFT`. To anchor a multi-line comment, add `start_line` plus `start_side`.

`suggestion` blocks post as normal comment bodies — GitHub renders a ` ```suggestion ` fenced block as a one-click "commit suggestion" button automatically.

## Top-level PR comment (fallback)

For a finding that isn't tied to a specific line, or when the diff position can't be resolved:

```bash
gh pr comment <number> --body "<comment text>"
```

## Attribution

Posted comments carry **no** AI-attribution markers — no "Generated by", no tool footers — matching the repo's commit/PR convention. Just the review content.

## After posting

Report back what was posted (count + the PR URL) and what was skipped. Don't re-run the reviewers; if the user wants another pass after they push fixes, that's a fresh `review-pr` invocation.
